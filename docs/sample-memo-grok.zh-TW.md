# Token 成本檢視 — 2026-10-12 至 2026-10-19

## 結論

1. 照目前的速度，你的 bot 每週約花 **$158**（每天約 $22.61），為依 token 換算的等值。照這個速度，額度約 3 天用完；要撐滿 7 天，得降到每週約 **$68**（少 57%）。
2. **其中 98% 在 grok-bot-default**；全部花費中 98% 是在重讀上下文，而不是產出內容。光是 **monitor** 一個 bot 就占全部花費的 50%（排程：every 30m）。
3. 下面的建議每週約可省 **$72–$119（45%–75%）**，每一塊錢只算一次；做完之後額度約可撐 **5.5–12.0 天**（目標 7 天）。

整體信心：**中**。

**做法**

1. 修改 monitor 的排程；若有少數事件需要即時處理，改成事件發生時直接通知它，而不是靠高頻輪詢。
2. 把規則寫進每個 bot 的指令，讓它在上下文超過門檻時自己交接：寫交接摘要（目標、決策、未完成事項，3K token 以內），再用它開新 chat。省量已扣掉每一次交接的成本；門檻的選法保證每個上下文每週交接次數不超過下方表格的上限。
3. 修改 heartbeat 的排程；若有少數事件需要即時處理，改成事件發生時直接通知它，而不是靠高頻輪詢。
4. 小內容直接放進訊息；大內容指明要讀哪一段。
5. 固定指令放最前面且不要改；避免修改或重排前面的訊息與工具清單。
6. 不要暫停它，也不要改它的頻率。列出每個可能擁有者的例行工作與觸發方式（排程、事件、webhook），並對上這些喚醒。先確認擁有者與觸發原因。

## 需要的決定與資料

- grok-bot-default 中有 44% 的花費（每週 $70）是未歸屬流量（你的訊息、bot 之間的通知，以及事件觸發的自動化）。先確認擁有者與觸發原因：列出每個可能擁有者的例行工作（排程、事件、webhook）並對上這些喚醒，或用 --events 傳入事件開始時間。在那之前不要暫停它，也不要改它的頻率。
- 要達到每週 $68，在上述行動之外還差約每週 $19：決定哪些工作可以降低頻率，或提高預算。
- 100% 的呼叫沒有 Automation ID，只能依模型分組（grok-bot-automation, grok-bot-default）；這些分組裡混了好幾個 bot。排程檔已把 56% 的花費歸到 3 個具名的 bot，其餘仍無法歸屬。**做法：**取得每個 bot 的拆分：逐一篩選 bot 匯出、各自跑報告，或把例行工作改成具名的自動化，讓 id 有值。
- 沒有 chat／thread 編號，不同 chat 的呼叫混在一起：上下文大小、成長和重置都是混合值。**做法：**匯出時帶 chat 編號；做不到的話，直接記下主要 chat 的上下文大小（每個 chat 抽一次就夠）。
- 成本是方案內計費（Included／Free），美元是從 token 換算的等值，不是帳單；用來比較方案、當作額度消耗的代理指標。**做法：**不需修正；把美元當相對值看。

### 附錄 — 方法與假設

- 期間：2026-10-12 08:00 – 2026-10-19 07:31 (UTC+08:00)（7.0 天、1,236 次呼叫）。每週數字 = 期間 × 7 ÷ 天數。
- 價格：grok-4.7 設定（輸入 $2.0/M、快取 $0.5/M、輸出 $6.0/M；200,000 token 起為長上下文價格）。
- 依據等級：**實測** = 這份匯出中該模式已經花掉的錢（區間 = 去掉一半到全部）；**模型** = 成本模型的推估（校正誤差在 ±15% 內才採信）；**判斷** = 敏感度區間，不是預測。
- 校正：模型 $143.03，期間實際 $157.83（-9.4%）。
- 一次喚醒 = 同一上下文中間隔不超過 120 秒的連續呼叫。
- 排程比對：在排程觸發前 60 秒到觸發後 300 秒內開始的喚醒，歸給該排程；距離最近者優先，每次觸發只對一個喚醒。無事可做 = 只呼叫一次、輸出最多 80 token。降低頻率的省量 = 實測每次喚醒成本 × 減少的喚醒次數（區間 70–100%）。
- 使用的欄位：time=Date, bot=Automation ID, output=Output Tokens, model=Model, input=Input (w/ Cache Write) + Input (w/o Cache Write) + Cache Read, cached=Cache Read。
- 完整的逐上下文明細：對同一個檔案跑 `bto analyze`。
